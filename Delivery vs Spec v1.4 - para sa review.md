# Delivery Management vs HomeCartel Spec v1.4 — para sa review mo

Binasa ko ang **buong specification package** (`HomeCartel Supply Chain System - Specification v1.4`), hindi lang ang folder na "04 Delivery": lahat ng 30 markdown file sa `Source (Markdown for developers and Claude)/` (00 Overview hanggang 07 Migration), at ang `08 Design Doc` na English PDF (78 pages, via `pdftotext`, dulo hanggang dulo — hindi binasa nang buo ang Tagalog version, 2 pages lang ang sinuri para kumpirmahin na "Pareho ang laman" talaga, nakasulat mismo sa file). Tiningnan ko rin ang mga dati nang vault note (`Checklist - Delivery Missing Functions.md`, `Plan - Delivery Management.md`, `Open Decisions - Delivery Management.md`, `Decision - Delivery Clock Divergence.md`) at ang aktwal na code sa `server/modules/delivery-management/*.mjs` at `modules/Delivery Management/*`. Pinatakbo ko ang buong Delivery test suite (127/127 pass).

## 1. Ang pinaka-importanteng natuklasan, bago lahat

**Ang Delivery Management code na nasa repo ngayon ay 1:1 na port lamang ng LUMANG Zoho Creator system — hindi pa ito ang bagong v1.4 na disenyo.** Ito ang pinakamalaking pagkakaiba sa Procurement, na dumaan na sa sariling "i-apply ang spec v1.4" na proyekto (makikita sa `Procurement vs Spec v1.4 - para sa review.md` at sa dose-dosenang Change Log entries). Delivery, wala pang ganitong ginawa.

Patunay, mula sa `vault/Plans/Plan - Delivery Management.md` (petsa 2026-11-12, **bago pa** magsimula ang Procurement v1.4 work na 2026-11-13+): ang buong plano ay "i-port ang 16 workflows at 6 custom APIs" mula sa Zoho Deluge — `SA_Scheduling_Engine`, `EXC_Resolve_Sync`, `dmsScheduleSlot`, atbp. — sinadyang pinapanatili ang mga Zoho quirks ("mirrors Zoho" sa code comments), hindi ang bagong disenyo. Na-kumpirma ko ito sa code mismo:

| Bagay na sinasabi ng v1.4 spec na dapat meron | Nakita ba sa `server/modules/delivery-management/*` |
|---|---|
| `category` / `queue_rank` / `priority_reason` / `suggested_action` (sorting engine) | **Wala.** Zero match sa buong module. Meron ito sa Procurement at Fulfillment, wala sa Delivery. |
| `day_plans`, team rotation (mod 7 / mod 11 algorithm) | **Wala.** |
| Field App bilang offline-first PWA (IndexedDB, service worker) | **Wala.** Ang "Ongoing Service" / "Field Service Site Visits" ay regular na server-rendered widget, hindi PWA, walang offline queue. |
| 12-line Site Requirements Checklist | **Wala.** |
| Tracking page (`/t/<token>`) | **Wala.** |
| Third-party booking (Lalamove) | **Wala.** |
| Job status chain `requested→scheduled→confirmed→dispatched→on_site→done(complete/partial/failed)→archived` | **✅ 2026-11-18 (ang status chain mismo), ❌ pa rin ang `partial` outcome.** `job-status.mjs`: bagong `Job_Status` field, computed mula sa fields na meron na (sumasama lang, hindi papalit sa `Appointment_Status`). `on_site` mula sa Field_Work's "Status: Started"; `archived` mula sa bagong nightly job. **Walang `partial` outcome pa rin** — "outcome calculated from item results" (FA-R1) ay hindi pa magawa: isang Field App ang ginawa para dito mamaya ring araw na iyon, pero inalis ito ng owner (nahanap na ang Ongoing Service → Exception Queue path ay sapat na, tingnan ang §4.4). |
| Approval queue kinds na Delivery (`third_party_booking`, `force_close`) | **✅ 2026-11-18, pareho na.** `suggest-schedule.mjs` at `failure-redelivery.mjs`, gamit ang shared `Approval_Queue` form (dati Procurement-only gamit, pero 05/06 Shared Engine talaga, hindi Procurement-only sa spec). |

Ang mga form na ginagamit pa rin ngayon ay ang mga LUMANG pangalan ng Zoho (`Service_Appointment_Form`, `Delivery_Scheduling`, `DMS_Exception_Queue`, `Daily_Team_Availability`, `Service_Request1`) — wala sa mga ito ang mga bagong table ng spec (`service_requests`, `delivery_jobs`, `day_plans`, `team_availability`, `job_events`, `job_line_results`, `job_proofs`, `signature_links`).

**Ibig sabihin: halos lahat ng 9 dokumento ng "04 Delivery" ay hindi pa ginawa ayon sa bagong disenyo** — hindi dahil may sira, kundi dahil hindi pa ito ang ginawang proyekto. Ang port ay solid para sa SARILING saklaw nito (127/127 test pass, isang tunay na bug pa nga ang naayos sa daan — tingnan [[Decision - Delivery Clock Divergence]]), pero ibang bagay ang tinatanong ng v1.4 checklist.

### Tungkol din sa buong tech stack (hindi lang Delivery)

Ang Decision Log (`00 Overview / 02 Decision Log.md`, D1–D2) ay malinaw: "Python (FastAPI) backend... HTMX office screens, React PWA for the field app" ang **opisyal na desisyon**, kapalit ng "Node stack." Ang **buong repo na ito** (Procurement kasama) ay nakasulat sa Node.js + vanilla JS widgets, hindi Python/FastAPI/Supabase/HTMX/React. Hindi ito Delivery-specific na problema — pang-buong-proyekto ito. Ang paliwanag na nakita ko (Design Doc, p. 71 ng 78, "One system... LocalSystem is the new one"): ang kasalukuyang Node repo ("LocalSystem") ay opisyal na **simula** ng bagong sistema, hindi isang ikalawang/itatapon na sistema — kaya hindi ito nangangahulugan na kailangang itapon ang lahat; pero kung titingnan nang literal ang spec, wala pa ring Python/Supabase/HTMX/React PWA kahit saan. Hindi ko na gagawin pang muling i-flag ito sa bawat item sa ibaba — isang beses lang dito, at sa mga sumusunod na tsart ay ang **patakaran/behavior** ang sinusuri ko (parehong pamamaraan ng Procurement review), hindi ang programming language.

## 2. Ano talaga ang hinihingi ng spec (buod)

Siyam na dokumento sa "04 Delivery": (1) Service Request + Site Checklist + earliest-date, (2) Scheduling Engine + Team Rotation, (3) Appointment, Dispatch + Load Sheet, (4) Field App, (5) Failure/Redelivery/Exception Queue, (6) Customer Notifications + Tracking Page, (7) Sales Returns + Archive, (8) Site Visits + Truck Maintenance, (9) Delivery Analytics. Lahat ay gumagamit ng parehong Sorting Engine (05/01), Calculators (05/02), Dates/Forecast (05/03), Timestamps (05/04), Exceptions/Alerts (05/05), Approval Queue (05/06), Control Panel (05/08), at kumokonekta sa SMS/Viber/Email/Files (06/02) at Zoho Books/Inventory (06/01).

## 7. Ano ang maganda sa kasalukuyang Delivery code (hindi dapat kalimutan)

- Ang 16 workflows + 6 custom APIs ng LUMANG Zoho system ay **buo at sinubukan** (127/127 test pass ngayon), kasama ang isang tunay na bug na natagpuan at naayos (`Decision - Delivery Clock Divergence.md` — ang `10.3:00 AM` na hindi valid na oras sa Zoho, naayos na sa port).
- May mga desisyon na malinaw at sinagot na (`Open Decisions - Delivery Management.md`): CMS/Books nananatiling external (A1=A), Schedule Requests tinanggal para sa Service Request na (A2, 2026-11-14), atbp.
- Ang mga bagay na "sinadyang hindi ginawa" dito (hal. ang third-party booking, PWA) ay hindi dahil nakalimutan — wala pa talagang gumawa ng hiwalay na "apply v1.4 to Delivery" na proyekto. Ibang usapin ito kaysa sa "may sirang code."

## 8. Mungkahi (hindi ko ito ginawa, mungkahi lang)

Kung gagawin ang parehong proseso na ginawa sa Procurement (11 hakbang, bawat isa may sariling commit, test, at review), ang pagkakasunod-sunod na mukhang pinaka-makatwiran base sa spec's sariling Build Phases (`00/04`, hakbang 4 at 5):

1. **Sorting engine para sa Delivery** (categories, queue_rank) — pareho ang pattern sa Fulfillment's `sorter.mjs`, pinakamadaling simulan dahil may existing na halimbawa.
2. **Site Checklist + Service Request bagong anyo** — kailangan bago ang scheduling engine makapag-"earliest date" nang tama.
3. **Team rotation job** — pinaka-kinatakutang "sleeper" risk base mismo sa Design Doc (p.16-17): kung walang automated na `team_availability`, lahat ng ibabaw nito ay sablay.
4. **Job status chain + per-line results** — kailangan bago ang "outcome calculated, never chosen" na tuntunin ay magawa.
5. Lahat ng iba pa (load sheet, tracking page, SMS, third-party, sales returns bagong anyo, analytics) ay umaasa sa 1-4.

Pero desisyon mo kung saan talaga simulan — hindi ko ito gagawin nang wala kang sinabi.
